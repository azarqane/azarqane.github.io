Socle Infrastructure : Vault, Bastion & GitLab Runner

La phase 01 installe les fondations sur lesquelles toutes les autres phases reposent. Sans elle, aucune pipeline CI/CD ne peut s'exécuter, aucun secret ne peut être injecté, aucun accès réseau ne peut être établi. L'ordre de déploiement est strict : GitLab Runner (LXC) → Vault (VM) → Bastion Tailscale (LXC) → enregistrement Runner. Tout est rejouable via scripts/deploy_all.sh.

Composants & responsabilités

  • GitLab Runner LXC (Docker Executor)Conteneur LXC non-privilégié avec nesting: true pour Docker-in-LXC. Double interface réseau (eth0 Internet + eth1 vmbr2). Concurrence = 4 jobs parallèles. S'auto-enregistre via le token extrait de Vault.
  • HashiCorp Vault (VM QEMU Cloud-init)VM Ubuntu 22.04 full-clone. TLS auto-signé via OpenSSL (SAN IP). Stockage fichier sur /opt/vault/data. Moteur JWT/OIDC lié à GitLab.com. KV v2 : secret/projet_devops contient 17+ secrets.
  • Bastion Tailscale LXC (Subnet Router)LXC ultra-léger (1 vCPU / 512 Mo). Module TUN configuré au niveau Proxmox via /etc/pve/lxc/VMID.conf. Annonce le sous-réseau 10.0.1.0/24 dans le réseau Tailscale. IP Forwarding activé.
  • Scripts d'orchestration (Bash)deploy_all.sh : 6 étapes séquentielles. load_env.sh : sourcage compatible bash/zsh du fichier .env. destroy_all.sh : destruction avec mode auto-approve paramétrable.

I. Orchestration — deploy_all.sh (6 étapes séquentielles)

Le déploiement complet est rejouable en une seule commande. L'ordre est intentionnel : Terraform crée les ressources, puis Ansible configure dans le bon ordre de dépendance.

deploy_all.sh — Séquence
#!/bin/bash
set -e   # stop immédiat en cas d'erreur

# [1/6] Charge le .env (bash/zsh compatible)
source "$SCRIPT_DIR/load_env.sh"

# [2/6] Terraform : LXC Runner + VM Vault + LXC Bastion
cd terraform && terraform init && terraform apply -auto-approve

# [3/6] Vault : TLS + init + unseal + JWT + KV injection
ansible-playbook -i inventory.yml vault.yml

# [4/6] Bastion : TUN LXC + Tailscale Subnet Router
ansible-playbook -i inventory.yml bastion.yml

# [5/6] Runner : Docker + enregistrement GitLab
ansible-playbook -i inventory.yml runner.yml

# [6/6] Copie cert Vault sur le Runner (tag cert)
ansible-playbook -i inventory.yml runner.yml --tags cert
load_env.sh — Sourcage universel
# Compatible bash et zsh (détecte automatiquement le shell)
if [ -n "$BASH_SOURCE" ]; then
    SCRIPT_DIR="$( cd "$( dirname "${BASH_SOURCE[0]}" )" && pwd )"
elif [ -n "$ZSH_VERSION" ]; then
    SCRIPT_DIR="$( cd "$( dirname "${(%):-%x}" )" && pwd )"
fi

# set -a : exporte toutes les variables du .env
set -a && source "$ENV_FILE" && set +a
destroy_all.sh — Mode sécurisé
# Mode interactif par défaut, auto-approve optionnel
if [ "${TF_DESTROY_AUTO_APPROVE:-}" = "1" ]; then
  terraform destroy -parallelism=1 -auto-approve
else
  terraform destroy -parallelism=1  # confirmation manuelle
fi

III. HashiCorp Vault — TLS + Init + JWT + KV Injection

Le playbook vault.yml (296 lignes) est le plus critique de la phase 01. Il transforme une VM vierge en gestionnaire de secrets sécurisé, auto-signé, initialisé et configuré pour l'authentification GitLab JWT — sans aucune intervention manuelle.

Étape 1/4 — TLS Auto-signé (SAN IP)
# Certificat avec Subject Alternative Name (IP)
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/vault.d/tls/vault.key \
  -out    /etc/vault.d/tls/vault.crt \
  -subj   "/C=FR/ST=Paris/O=DevOps/CN={{ ansible_host }}" \
  -addext "subjectAltName=IP:{{ ansible_host }},IP:127.0.0.1"
# Propriétaire : user vault, mode 0600
vault.hcl — Configuration HTTPS
ui = true
disable_mlock = true

storage "file" {
  path = "/opt/vault/data"
}

listener "tcp" {
  address       = "0.0.0.0:8200"
  tls_disable   = 0              # HTTPS obligatoire
  tls_cert_file = "/etc/vault.d/tls/vault.crt"
  tls_key_file  = "/etc/vault.d/tls/vault.key"
}

IV. Bastion Tailscale — Subnet Router & Accès Zero-Trust

Le bastion est un LXC ultra-léger qui annonce tout le sous-réseau Proxmox (10.0.1.0/24) dans le mesh Tailscale. Depuis un PC admin authentifié sur Tailscale, l'accès SSH direct à toutes les VMs du réseau interne est immédiat — sans VPN, sans port ouvert.

Plateforme IaC : Cluster K3s & GitOps

La phase 02 transforme l'infrastructure brute en une plateforme CaaS (Container as a Service) entièrement auto-réparante. Chaque composant — du provisioning VM au tunnel Cloudflare, en passant par les politiques de backup et la restauration — est versionné dans Git et rejouable en un seul déclenchement de pipeline. Zéro intervention manuelle.

Composants & responsabilités

  • K3s v1.32.2+k3s1 — Control Plane1 Master + N Workers scalables via count. Token de jonction partagé cross-host via Ansible delegate_to. Kubeconfig exporté et patché automatiquement.
  • Longhorn v1.7.2 — Stockage Distribué2 réplicas synchrones par PVC. Prépare dm_crypt, open-iscsi, blacklist Multipath. Disques labellisés par nœud.
  • ArgoCD — GitOps Self-Healing3 envs isolés (dev/staging/prod). selfHeal: true + prune: true. Endpoints K8s natifs vers MariaDB externe.
  • MariaDB & MinIO — Services ExternesIntentionnellement hors cluster. MariaDB : 3 bases dédiées par env. MinIO : stockage S3 sur disque dédié 40 Go + sync Rclone → Cloudflare R2 toutes les 5 min.
  • Cloudflared — Tunnel HTTPS PublicDéployé dans K3s avec replicas: 2. Token Cloudflare injecté via Secret K8s. Aucun port ouvert sur la box. Limites CPU/RAM définies.

IV. Deployment K8s — Pattern Sidecar & Haute Disponibilité

Un seul pod contient deux conteneurs qui partagent le même volume /var/www/html. Nginx sert les statiques directement et délègue le PHP à FPM via 127.0.0.1:9000 (loopback dans le pod). Le podAntiAffinity garantit que les 2 réplicas sont sur des nœuds différents.

Pattern Sidecar — volume partagé
spec:
  replicas: {{ .Values.replicaCount }}  # 2
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            topologyKey: kubernetes.io/hostname
            # → pods répartis sur nœuds différents

  volumes:
    - name: wordpress-files
      persistentVolumeClaim:
        claimName: wordpress-pvc       # Longhorn 5Gi RWX
    - name: nginx-config
      configMap:
        name: nginx-config             # proxy FPM

  containers:
    - name: wordpress                  # port 9000
      volumeMounts:
        - mountPath: /var/www/html     # fichiers WP

      volumeMounts:
        - mountPath: /var/www/html     # même volume
        - mountPath: /etc/nginx/conf.d/default.conf

V. ConfigMap Nginx — Proxy FastCGI & Sécurité

La configuration Nginx est injectée via ConfigMap, ce qui la rend versionnable et rechargeable sans rebuild d'image. Les fichiers statiques sont servis avec 30 jours de cache, les fichiers sensibles (.ht, .git, .env) sont bloqués.

server {
    listen 80;
    server_name {{ .Values.ingress.host }};  # injecté par Helm
    root /var/www/html;
    index index.php;

    # Statiques : servis directement par Nginx (cache 30j)
    location ~* \.(jpg|jpeg|png|gif|ico|css|js|woff|woff2|ttf|svg)$ {
        expires 30d;
        add_header Cache-Control "public, no-transform";
        try_files $uri $uri/ =404;
    }

    # Réécriture WordPress (pretty permalinks)
    location / {
        try_files $uri $uri/ /index.php?$args;
    }

    # Proxy PHP → FPM sidecar (loopback dans le pod)
    location ~ \.php$ {
        fastcgi_pass 127.0.0.1:9000;
        fastcgi_index index.php;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
        fastcgi_read_timeout 300;
        fastcgi_buffer_size 16k;
        fastcgi_buffers 4 16k;
    }

    # Sécurité : bloquer fichiers sensibles
    location ~ /\.(ht|git|env) { deny all; }
}

Phase 2 : Dépôts Locaux & Redondance Géographique

La sécurité des sauvegardes repose sur leur dispersion physique. Pour ISATIS, deux NAS haute performance ont été déployés dans deux bâtiments distincts, reliés par la colonne vertébrale fibre du site, afin de prévenir tout risque lié à un sinistre localisé (incendie, dégât des eaux).

NAS 01 : Repository Primaire

  • Bâtiment A (Centre Technique)Cible principale des jobs de sauvegarde. Stockage des Full hebdomadaires et des incrémentales quotidiennes.
  • Rétention Rapide (14j)Conservation sur disque pour une restauration quasi-instantanée en cas d'erreur utilisateur ou de crash applicatif.
  • RAID 5 / BtrfsProtection contre la panne d'un disque physique et vérification de l'intégrité des fichiers (Self-healing).

NAS 02 : Réplique de Secours

  • Bâtiment B (Aile Administrative)Stockage secondaire recevant une copie mirroir du repository primaire via un job de "Backup Copy".
  • Isolation RéseauVLAN dédié aux flux de sauvegarde pour éviter toute interception ou saturation du réseau utilisateurs.

Mécanismes de protection des données

Les NAS sont configurés pour résister non seulement aux pannes matérielles, mais aussi aux tentatives de compromission logique.

Credentials Isolés

Les partages de sauvegarde ne sont accessibles que par le compte de service Veeam, aucun accès "utilisateur" direct n'est autorisé.

Monitoring SNMP

Remontée d'alertes en cas de pic de température, de disque défectueux ou de tentative de connexion suspecte.

Phase 3 : Externalisation Cloud & Immuabilité

En complément de la redondance locale, une copie externalisée est indispensable pour parer aux catastrophes majeures. Pour ISATIS, nous avons opté pour Cloudflare R2, une plateforme de stockage objet compatible S3 offrant une résilience mondiale et une tarification optimisée sans frais de sortie de données (Egress).

Technologie Cloudflare R2

  • Stockage S3-CompatibleIntégration transparente dans Veeam comme un "External Repository" via les clés d'accès API.
  • Pas de frais d'EgressContrairement aux géants du Cloud, le téléchargement des données lors d'une restauration est gratuit, facilitant les tests de PRA.
  • Haute DisponibilitéDonnées répliquées sur plusieurs infrastructures Cloudflare pour une durabilité maximale.
Sécurité : L'Immuabilité (Object Lock)

Cloud Object Lock :

Une fois écrite dans le bucket R2, la sauvegarde est rendue immuable pendant 30 jours. Aucune suppression n'est possible, même avec des identifiants compromis, protégeant ISATIS contre les ransomwares destructeurs.

Logique de Transfert (Capacity Tier)

Veeam gère intelligemment le cycle de vie des données. Les sauvegardes récentes restent sur les NAS (Performance Tier) pour la rapidité, tandis que les archives anciennes sont automatiquement déchargées vers le Cloud.

Sobriété & Efficacité
  • Déduplication Cloud : Seuls les blocs uniques non présents dans le Cloud sont transférés.
  • Chiffrement Source : Les données sont chiffrées par Veeam avant de quitter le serveur ISATIS.
  • Rétention GFS : Conservation de 12 sauvegardes mensuelles dans le Cloud pour l'historique légal.
